# Разбор System Trace

Анализ четырёх записей от 05.10.2026. Основная статистика лабораторной не меняется: трассы используются для объяснения поведения, отдельно от 120 итоговых запусков.

## Методика

Экспорт выполнен через xctrace: таблицы context-switch, thread-state и time-profile. Рассматривается только Main Thread целевого PID. Все XML id/ref раскрываются в пределах документа. Начальная синтетическая блокировка от нуля времени трассы до первого события планировщика исключена. Проверено, что сумма интервалов состояний совпадает с длиной диагностического окна.

Профиль ниже группирует верхний кадр пользовательского стека по весу выборки. Например, read на вершине стека может соответствовать выполнению системного вызова в ядре; это не прямое измерение kernel time. Оценки согласуются с независимым user/sys из основной серии. Веса выборок не равны количеству вызовов; карту syscall-name-map нельзя использовать как счётчик вызовов.

## Профиль

| Режим | Обходов | Выборок | Основные верхние кадры: доля веса |
|---|---:|---:|---|
| graph_traverse-read | 20 | 4328 | read 57.0%; __lseek 42.5%; main 0.3% |
| graph_traverse-write | 20 | 19822 | write 51.8%; __lseek 28.1%; read 19.6% |
| graph_traverse_mmap-read | 1000 | 4817 | main 99.1%; __open 0.4%; __munmap 0.4% |
| graph_traverse_mmap-write | 1000 | 4881 | main 98.6%; __munmap 0.6%; __open 0.6% |

В read/lseek профиль сосредоточен в обёртках read/lseek; при обновлении появляется существенная доля write. В mmap почти весь профиль находится в main: оптимизатор встроил в него цикл обхода. Это поддерживает объяснение преимуществ mmap стоимостью системных вызовов при работе с файловым кэшем.

## Планировщик и ожидания

| Режим | Наблюдаемое окно, с | Running, % | Blocked, с | Смены ядра | Ядра |
|---|---:|---:|---:|---:|---|
| graph_traverse-read | 7.506 | 96.89 | 0.2223 | 19 | 8, 9, 10, 7, 6 (P) |
| graph_traverse-write | 27.815 | 98.58 | 0.3598 | 46 | 10, 8, 6, 9, 7 (P) |
| graph_traverse_mmap-read | 4.857 | 98.80 | 0.0383 | 8 | 9, 7, 6, 8 (P) |
| graph_traverse_mmap-write | 4.883 | 99.61 | 0.0019 | 2 | 9, 10, 8 (P) |

Смена ядра определяется как изменение номера CPU между соседними интервалами Running одного основного потока; промежуточные Interrupted/Blocked не обнуляют предыдущий CPU. Во всех четырёх трассах наблюдались только P-ядра. Running занимает большую часть экспортированного окна, поэтому по этим наблюдениям ожидания не доминируют. Interrupt-события не считаются переключениями между процессами: счётчики context-switch XML и getrusage имеют разные определения.

## Ограничения

- Трассы: по 20 обходов read/lseek и по 1000 mmap. Отдельные запуски в разное время, без статистической серии профилирования. Нельзя напрямую сравнивать абсолютные числа событий и общие длительности.
- Конец окна thread-state определяется экспортированными интервалами; в read/lseek Read отсутствует событие ThreadTermination. Последний Running может быть продолжен до конца записи. Поэтому значения окна и доля Running описывают представление Instruments, а не строгое время жизни процесса.
- В начале трассы есть запуск/инициализация, в конце — остановка записи. Профилировщик меняет условия; эти времена не добавляются в итоговые CSV и не используются для оценки его overhead. Другое число обходов также меняет долю стоимости запуска.
- Пользовательские стеки показывают верхний кадр. Без отдельных kernel call stacks и полного экспорта syscall нельзя установить точную долю каждой операции в ядре или фактическое число read/write/lseek.
- Наблюдение только P-ядер не доказывает отсутствие любых миграций или одинаковую частоту между сериями. Числа смен ядра относятся только к данным трассам.

## Воспроизведение

```sh
bash scripts/export_traces.sh
out/venv/bin/python scripts/analyze_traces.py
```

Экспорт XML: results/system-trace/. Сводка: results/system-trace/summary.json. Исходные трассы: mac-check-20261005-100726/*.trace. Итоговый отчёт: report/main.typ.
